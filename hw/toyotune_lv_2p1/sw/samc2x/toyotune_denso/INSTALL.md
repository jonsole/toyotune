# Building the SAMC21 firmware outside Atmel Studio

This project can be built from VS Code (or any terminal) with CMake + Ninja and
the Arm GNU toolchain, with **no Atmel/Microchip Studio install**. The Atmel
Studio project (`toyotune_denso.cproj`) still works and both produce the same
binary — see "Keeping the two builds in step" at the end.

## 1. Toolchain

In an **elevated** shell:

```
choco install cmake --installargs 'ADD_CMAKE_TO_PATH=System'
choco install ninja
choco install gcc-arm-embedded
```

Then open a new shell (so PATH refreshes) and check:

```
cmake --version && ninja --version && arm-none-eabi-gcc --version
```

Verified working with CMake 4.4.3, Ninja 1.13.2, and GNU Arm Embedded 10.3.1
(10.3-2021.10).

If the toolchain is installed somewhere not on PATH, set `ARM_TOOLCHAIN_DIR`
(see step 4) instead of adding it to PATH.

## 2. Device packs — **mind the version**

The build needs two sets of vendor headers:

| Pack | Provides | **Use version** |
|---|---|---|
| SAMC21 DFP | `sam.h`, `samc21j18a.h` | **1.2.176** (anything pre-3.0) |
| CMSIS | `core_cm0plus.h` and friends | 5.4.0, but **6.3.0 verified working** |

> **The DFP major version matters, and 3.x will not work.** This is the single
> biggest trap here.
>
> Microchip rewrote the headers at DFP 3.0, switching to the MPLAB Harmony
> style: peripherals became `SERCOM0_REGS` of type `sercom_registers_t`. This
> firmware is written against the older Atmel CMSIS style, where the same
> peripheral is `SERCOM0->USART` of type `SercomUsart` — as in `TC0->COUNT8`
> and `CAN0->CCCR` throughout `sdl.c`, `can.c` and `sercom.c`.
>
> These are two different APIs, not a set of renamed macros, so a compatibility
> header cannot bridge them. Building against DFP 3.9.248 yields **300 errors
> across 8 files** (`can.c`, `clk.c`, `diag.c`, `dmac.c`, `evsys.c`, `sdl.c`,
> `sercom.c`, `xmem.c`) covering 70 distinct missing symbols — including the
> peripheral instance pointers themselves. Nothing is wrong with the code.
> Porting it to Harmony headers would mean rewriting every register access
> *and* would break the Atmel Studio build.

### Where to get them

Use the **legacy Atmel pack server**, which still hosts the old versions:

> **http://packs.download.atmel.com/**

```
Atmel.SAMC21_DFP.1.2.176.atpack
ARM.CMSIS.5.4.0.atpack
```

These are the exact versions the Atmel Studio project uses, so they remove all
doubt. Note the `Atmel.` vendor prefix — these predate the Microchip rebrand.

The newer `packs.download.microchip.com` only goes back to DFP 2.0.5. That
would probably work too, since the header rewrite landed in 3.0, but it is
untested here — prefer the legacy server and the versions above.

`.atpack` files are ordinary ZIPs — rename to `.zip` (or unzip directly) into
`hw/toyotune_lv_2p1/sw/packs/`, so that these two directories exist:

```
sw/packs/SAMC21_DFP/samc21/include/sam.h
sw/packs/CMSIS/CMSIS/Core/Include/core_cm0plus.h
```

Those are the default locations the build looks in, so nothing further is
needed if you extract there. **The packs are not committed** — roughly 108 MB
of third-party headers, freely re-downloadable — so a fresh clone has to do
this step.

## 3. VS Code

Open the **repository root** as the workspace (not this directory), so `roms/`
and `hw/` are available together. `.vscode/settings.json` at the root points
CMake Tools at this project via `cmake.sourceDirectory`.

Recommended extensions (`.vscode/extensions.json` will prompt): CMake Tools,
C/C++, and Cortex-Debug if you intend to debug on hardware.

Pick a preset from the status bar and build. IntelliSense is fed from
`compile_commands.json` generated by CMake, so include paths and defines never
need duplicating.

## 4. Building from a terminal

```
cmake --preset mr2-cpu1-debug
cmake --build --preset mr2-cpu1-debug
```

Presets are named `<car>-cpu<n>-<config>`:

| Preset | Build |
|---|---|
| `mr2-cpu1-debug` | MR2 (D151803-9651), `-O0 -g3` |
| `mr2-cpu1-release` | MR2 (D151803-9651), `-Os` |
| `mr2-cpu2-debug` | MR2 CPU2 — **expected to fail**, see below |
| `st205-cpu1-debug` | ST205 (D151804-0461) — **expected to fail**, see below |

Two of these stop at a deliberate `#error` in `config.h`, because failing the
build beats silently flashing something wrong into a running ECU:

- **`mr2-cpu2-debug`** — CPU2 needs its own ROM image in `image.c` and its own
  DMA layout struct. Without them a CPU2 binary would parse CPU1's frames.
- **`st205-cpu1-debug`** — the *frame handling* is family-independent and
  already works for both cars, but `image.c` currently holds only an MR2 build,
  and this firmware writes that image into the SRAM the Denso CPU executes
  from. Building it today would run MR2 code on an ST205 ECU. Add the ST205
  image to `image.c`, selected on `TOYOTUNE_ECU_ST205`, then delete the
  `#error`.

The two axes are independent cache variables, so any combination is reachable
without editing presets: `-DTOYOTUNE_CPU=1|2` and `-DTOYOTUNE_ECU=MR2|ST205`.

### Machine-specific paths

If your packs or toolchain live elsewhere, do **not** edit `CMakePresets.json`
(it is shared). Create `CMakeUserPresets.json` beside it — already gitignored:

```json
{
  "version": 3,
  "configurePresets": [
    {
      "name": "local",
      "inherits": "cpu1-debug",
      "cacheVariables": {
        "PACKS_DIR": "C:/packs",
        "ARM_TOOLCHAIN_DIR": "C:/path/to/toolchain/bin"
      }
    }
  ]
}
```

`PACKS_DIR` expects `SAMC21_DFP/samc21/include` and `CMSIS/CMSIS/Core/Include`
beneath it; override `SAMC21_DFP_DIR` / `CMSIS_DIR` individually for a different
layout. A wrong pack path fails at configure time with a message naming the
variable, rather than dying later on a missing `sam.h`.

## 5. Output

In `build/<preset>/`:

- `toyotune_denso.elf` — with debug symbols
- `toyotune_denso.bin`, `.hex` — flashable images
- `toyotune_denso.lss` — disassembly listing
- `toyotune_denso.map` — link map

A size summary is printed after each build. A known-good `mr2-cpu1-debug` build is:

```
   text    data     bss     dec     hex
  47524    1124   15848   64496    fbf0
```

That is 48,648 bytes of flash (18.6% of 256K) and 16,972 bytes of RAM (51.8%
of 32K). Note 32,768 of the flash figure is the `DMCU_Image` ROM array in
`image.c`, leaving roughly 15.9 KB of actual code. `mr2-cpu1-release` (`-Os`)
comes out at 40,048 text.

Verified working: DFP 1.2.176 + CMSIS 6.3.0, GNU Arm Embedded 10.3.1,
CMake 4.4.3, Ninja 1.13.2.

## Troubleshooting

**`SAMC21_DFP_DIR does not exist`** — packs not unzipped, or unzipped
somewhere else. See step 2.

**Hundreds of `undeclared` errors on register names** — wrong DFP version.
See the warning in step 2.

**Undefined `_sbrk` / `_write` / `_close` at link time** — newlib is pulling in
syscall stubs. Add `--specs=nosys.specs` to `target_link_options` in
`CMakeLists.txt`.

**`multiple definition of ...` at link time** — GCC 10 defaults to
`-fno-common`, where older toolchains defaulted to `-fcommon` and silently
merged duplicate tentative definitions. Atmel Studio's build hid one such
duplicate (`Diag`, defined in both `diag.c` and `main.c`); that has been fixed
properly, with the single definition in `diag.c` and an `extern` declaration in
`diag.h`. If more surface, fix them the same way rather than adding `-fcommon`,
which only hides them again.

**CMake Tools does nothing in VS Code** — the workspace is probably opened at
this directory rather than the repo root, or `cmake.sourceDirectory` is not
being picked up. Reload the window after changing it.

## Keeping the two builds in step

`CMakeLists.txt` mirrors `toyotune_denso.cproj`: the same 18 source files, the
same flags (`-mcpu=cortex-m0plus -mthumb -std=gnu99 -ffunction-sections
-mlong-calls -Wall`, `-O0 -g3` debug / `-Os` release), the same defines
(`__SAMC21J18A__`, `OS_CPU_ID`, `DEBUG`) and the same linker script. **Change
one, change the other**, or the two will quietly diverge.

The source list is written out explicitly rather than globbed on purpose: this
directory also contains `mode.c`, `toyotune_avr.c`, `sram.c` and the `esp*`
set, which the Studio project does not compile. Several include `<avr/wdt.h>`,
`<avr/sleep.h>` and `<util/atomic.h>`, so a glob would drag AVR sources into an
ARM build.

The CPU selection differs slightly between the two: CMake passes
`-DTOYOTUNE_CPU1` / `-DTOYOTUNE_CPU2` on the command line, while Studio passes
neither and falls through to the default in `config.h`.
