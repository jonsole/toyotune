# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A reverse-engineering and ROM-tuning workspace for Toyota ECUs built on the **Toshiba/Denso 8X (D8X)** microcontroller — a proprietary MCU with an instruction set derived from the Motorola M68HC11. The repo covers disassembly, annotation, reassembly, and tuned-ROM production for multiple Toyota engine families.

This is a git repo (`origin` = `github.com/jonsole/toyotune.git`, also serving a GitHub Pages site off `master` — see `_config.yml`/`README.md`). There is no build system in the CI sense; "building" means reassembling one ECU's `.ASM` source back into a flashable binary via `make`.

## Repository layout

The repo has four top-level areas: **`roms/`** (disassembly/ROM-tuning workspace — the vast majority of the content and of this guide), **`hw/`** (Toyotune interface hardware — PCB, CPLD, host-MCU firmware and the bench stimulator), **`tools/`** (host-side bench tooling), and **`sw/`** (IDA Pro installs).

### `roms/`

- **Engine family directories** (`1G-GTE`, `1G-GZE`, `1JZ-GTE`, `1UZ-FE`, `3S-GE`, `3S-GTE`, `3VZ-FE`, `4A-GE`) — each contains one subdirectory per ECU part number (e.g. `D151803-9651`), plus person-named subdirectories (`Jon_ST205_ECU`, etc.) for individual custom-tune branches derived from a base ROM.
  - Within an ECU directory: `.ASM` (IDA-exported/hand-annotated disassembly), `.bin`/`.BIN` (ROM images), `.idb`/`.id0`/`.id1`/`.nam`/`.til` (IDA Pro database files — open the `.idb` in IDA to browse/edit the annotated disassembly), `.XDF` (TunerPro tune-definition files for map editing), `.xlsx` (extracted/diffed calibration maps), `Makefile`.
  - `toyotune/` — sources/images for the **Toyotune board** rather than for a stock ECU: the `*_DIAG16_*` variants, which are the base ROM modified to add diagnostic read/write support (the protocol `diag.c` talks to — **documented in full in `roms/3S-GTE/gen3/diag_protocol.md`**, which is the place to start before touching either side of it). These are hand-modified images, are *not* referenced by any `Makefile`, and must not be confused with `output/toyotune/`, which is generated build output.
  - `output/` — build artifacts: `build.txt` (assembler log), plain `.bin`/`.lst`, plus `output/toyotune/` (32K-padded image for the Toyotune flasher) and `output/techtom/` (scrambled/XOR-encoded image for the Techtom tool).
- **`- Copy` files** (e.g. `D151803-9651 - Copy.ASM`) are older, superseded snapshots (dated ~2018) kept alongside the live working file (dated 2020+). **Never treat a `- Copy` file as the one to edit** — always confirm which is current by timestamp/content before touching either.
- **`roms/docs/`** — reverse-engineering notes on the **D8X MCU itself**, which every engine family in the repo shares. ECU-specific write-ups live with their engine family instead (see `roms/3S-GTE/gen3/` below).
  - `toshiba-8x-technical-reference.md` — full instruction set, opcode matrix, registers, addressing modes for the D8X.
  - `toshiba-8x-reference-part1.md`, `-part2-appendix.md` — extended/appendix material for the above.
- **`roms/3S-GTE/README.md`** — the ROM→vehicle map for this engine family: which part number is which market (JDM/UK/USDM), which vehicle (SW20 MR2 Gen 1/2/3, ST205 Celica GT-Four), which half of a two-CPU pair, and what files exist for each. Start here when you need to know what a part number *is*.
- **`roms/3S-GTE/gen3/`** — the reverse-engineering write-ups for the Gen 3 SW20 pair (`D151803-9651`/`-9661`), the most heavily annotated ECU in the repo:
  - **`ecu_overview.md`** — architectural tour of the whole ECU (three-processor layout, inter-CPU DMA, timing/crank geometry, the fuel chain, the trims, knock, and the ROM-space idioms that make the disassembly hard to read cold). **The best entry point** before diving into a subsystem doc.
  - **`session_journal.md`** — the living progress log for the `D151803-9651` reverse-engineering effort. **Read this first when resuming work on that ROM.** It tracks completed subsystems and their key renames (`sub_XXXX` → meaningful name), a pending-work list of untouched chunks/functions, a key-variable reference table, and architecture notes (CPU1/CPU2 split, inter-CPU DMA, timer resolution, NE pulse geometry). Update it as new subsystems/functions are understood — append to "Completed subsystems", move items out of "Pending work", and add new renames to the variable reference table, rather than letting this knowledge live only in `.ASM` comments or chat history.
  - `knock_mcu_update.ASM` — a fully-annotated extracted routine (from `D151803-9651`) kept as a reference example of the target comment/annotation style: purpose header, per-branch behavior explained, flag semantics spelled out, cross-refs preserved. Use this as the bar for quality when annotating other functions.
  - **`diag_protocol.md`** — the diagnostic link between the Toyotune board and the running ECU: framing, the state machine, the read/write/block sequences poll by poll, atomicity, the RAM it uses, error handling and the measured error rates. Unlike its neighbours this one spans both trees — the ECU half is `serial_diag_extended` in the DIAG16 `.ASM`, the host half is `hw/.../diag.c` — so read it before changing either.
  - `adc_system.md`, `ignition_system.md`, `knock_sensor_system.md`, `idle_control_system.md`, `fuel_calculation_system.md` — polished, per-subsystem write-ups (ADC channel scanning, ignition timing/dwell scheduling, per-cylinder knock retard learning, idle speed control, base injector pulse-width calculation) distilled from the session journal once a subsystem is fully understood, including key symbol names, timing units, and hardware pin mappings.
- **`roms/bin/`** — compiled toolchain binaries: `Tasm32.exe`/`tasm8x.bat` (the original Table-driven Assembler for the D8X — kept for reference/cross-checking, no longer invoked by the Makefiles), `TASM8x.TAB` (opcode table, still used to cross-check the Python assembler), `checksum.exe`, `scramble.exe` (both still invoked by `make` — see below), `descramble_brute.exe`, `descramble_brute2.exe`, `make.exe`.

(Source projects for `scramble.exe`/`descramble_brute*.exe` were not carried over in this workspace transfer — only their compiled `bin/` binaries are present.)

- **`roms/verify_assembly_match.py`** — the canonical copy of the `.lst` comparison script (see "After editing" below); an identical duplicate also lives at `roms/3S-GTE/D151803-9651/Claude/verify_assembly_match.py`.

### `hw/`

- **`hw/toyotune_lv_2p0/`** — hardware design for the Toyotune interface board, v2.0: `pcb/` (Eagle `.sch`/`.brd`, OSH Park fab files, BOM) and `cpld/` (`toyotune_3s_lvc_dil28`, `toyotune_3s_lvc_plcc32` VHDL projects for the two package variants). Design files only — no firmware in this directory.
- **`hw/toyotune_lv_2p1/`** — Toyotune interface board v2.1, the current revision, built around an **Atmel/Microchip ATSAMC21J18A** (Cortex-M0+) host MCU. Unlike v2.0 this tree also carries the firmware and bring-up sources. Four subdirectories:
  - `pcb/` — Eagle design. `toyotune_3s.sch`/`.brd` (Dec 2020) is the live board; `toyotune_3s_coolrunner`, `toyotune_3s_lvc*`, `toyotune_3s_tsop`, `toyotune_usb*` and `can.sch` are older/experimental variants kept alongside it. Also fab configs for several houses (`elecrow*.cam`/`.dru`, `PCBWay_4_layer.cam`, `laen-*`, `gold-phoenix.dru`, `pcb-pool.dru`), `gerbers/` (the as-fabbed `jlcpcb_02062020.zip`). Loose gerber exports are deliberately **not** kept in the repo — regenerate them from the `.cam` jobs against the current `.brd`. Part libraries are `toyotune.lbr`, `jst-ph.lbr`, `con-jst*.lbr`, `SRG.lbr` and `usb_con-update.lbr`; `documents/` holds the AT29C256 flash datasheet.
  - `cpld/` — Xilinx ISE VHDL for the CPLD that sits between the board and the ECU. Four project variants (`toyotune_3s`, `toyotune_3s_lvc_dil28`, `toyotune_3s_lvc_dil28_romtune`, `toyotune_3s_lvc_plcc32`), each with `io_expander.vhd`, testbenches (`mem_read_tb`, `ext_mem_read_tb`, `io_write_tb`) and a built `io_expander.jed`. `cpld/roms/D151803-9651.BIN` plus `cpld/tools/gen_rom.bat` (wrapping `hex2rom.exe`) generate each project's `d151803-9651_rom.vhd`, which is a **simulation-only** ROM model — regenerate it rather than hand-editing.
  - `sw/` — host-MCU firmware and the host-side scripts that talk to it:
    - `sw/samc2x/toyotune_denso/` — **the current firmware.** ARM GCC, device `ATSAMC21J18A`, linker scripts `Device_Startup/samc21j18a_flash.ld`/`_sram.ld`. **Two build systems produce the same binary and must be kept in step:** the original Atmel Studio 7 project (`toyotune_denso.atsln`/`.cproj`) and a `CMakeLists.txt`/`CMakePresets.json` pair that needs no Studio install — presets are named `<car>-cpu<n>-<config>` (`mr2-cpu1-debug`, `mr2-cpu1-release`, `mr2-cpu2-debug`, `st205-cpu1-debug`), and the last two stop at a deliberate `#error` in `config.h`. **`INSTALL.md` is the authoritative build guide** — read it before fighting the toolchain, especially §2 on the device packs (the SAMC21 DFP must be pre-3.0; 3.x rewrote the headers to MPLAB Harmony style and yields ~300 errors) and §6 on the ROM image.

      **Core idea of the v2.1 board:** it carries a real SRAM that the Denso MCU executes from, and the SAMC21 loads that SRAM. The boot sequence in `main.c` is the thing to read first — `DMCU_Init()` holds the Denso MCU in reset, `XMEM_Init()` sets up the bus pins, the CPLD version register is read back over the same bus (`PanicFalse(CpldVersion == 4)` — though that check currently compiles to nothing, see the debug note below), `XMEM_BlockWrite(0x8000, DMCU_Image, 32768)` copies the 32K ROM image into SRAM at `0x8000`, then `DMCU_ResetDisable()` releases the Denso MCU, which now runs that code. So the "ROM" the ECU executes is ordinary RAM contents written by the SAMC21, not a flash/EPROM part — the image can be swapped without reprogramming anything.

      **The SRAM is shared between the two CPUs, and only one of them may drive the bus at a time.** Which one is decided by whether the Denso MCU is in reset, and that gives the firmware two mutually exclusive ways to reach memory:

      1. **Denso held in reset — direct access.** The SAMC21 owns the bus and reads/writes the SRAM itself through `xmem.c`. This is how the image is loaded, and `XMEM_BlockRead` can read it back the same way.
      2. **Denso running — no direct access.** Every `XMEM_BlockWrite`/`XMEM_BlockRead` ends by clearing `DIRCLR`/`OUTCLR` on all 16 bus pins, returning `DA0:7` and `A8:15` to inputs so the SAMC21 stops driving them and the Denso MCU can. (Only the address/data lines are released; the `!X_RD`/`!X_WR`/`X_ADR` strobes stay outputs, parked inactive.) From here the SAMC21 cannot touch the SRAM at all — it must **ask the Denso software** to do it for it, over the 1 MHz USART in `diag.c`.

      That second point is the key to reading `diag.c` correctly: its reads and writes are not hardware bus cycles but a cooperative protocol serviced by code running on the Denso MCU, which is exactly why the Denso is the protocol master and the SAMC21 only answers it.

      One further detail of the shared address space: not all of it is SRAM. The CPLD decodes two registers of its own inside it — `DMCU_REG_MEMC` (`0x1E`) and `DMCU_REG_VER` (`0x1F`) — which is why `XMEM_WriteEnable()` is not a SAMC21-side flag but an `XMEM_BlockWrite` of `0x01`/`0x00` to `0x1E`: SRAM write-enable is gated by the CPLD, not by the SAMC21's port directions. Denso reset itself is `!X_INIT` on `PA07` (`dmcu.c`), and `PA20` reports whether the Denso MCU has halted.

      Key modules: `xmem.c` (bit-banged multiplexed bus to the SRAM — `DA0:7` + `A8:15` on PORTB, `X_ADR` latch on PB30, `!X_RD`/`!X_WR` strobes on PB16/PB17; the port direction is flipped to inputs when idle so the Denso MCU can drive the bus), `dmcu.c` (reset/halt control of the Denso MCU, plus the `DMCU_Image[32768]` declaration — the image bytes themselves are the giant array in `image.c`), `os.c`/`os_pendsv.s` (small task kernel — PendSV context switch, signal/message waits), `sdl.c` (passive sniffer of the CPU1↔CPU2 link — see below), `diag.c` (live read/write link to the running Denso MCU — see below), `can.c`/`can_telemetry.c` (CAN and the telemetry tables), `ecu.h` (the inter-CPU DMA block structs plus the latest capture of each — the telemetry tables are driven off `offsetof()` into these, so a new ECU family is a branch here rather than new code), `dmac.c`, `evsys.c`, `sercom.c`, `clk.c`, `debug*.c`, and `toyotune.dbc` (the CAN database for host tooling). Be aware that **neither build compiles everything in the directory**: `mode.c`, `toyotune_avr.c`, `sram.c`, `reports.h` and the whole `esp*` set sit here but are **not in the build** (`CMakeLists.txt` lists sources explicitly and deliberately, precisely because a glob would pull in the AVR-era files and fail) — `mode.c`/`toyotune_avr.c` are AVR-era carryover (`IS_TOYOTUNE_BOARD`, `PSTR`) and `sram.c` is empty, `xmem.c` being the real implementation. `image.c` is **generated, not written** — see the ROM-image tool note below. It holds one 32K image, built from **`roms/3S-GTE/D151803-9651/toyotune/D151803-9651_DIAG16_32K.ASM`** — the *DIAG16* variant, not the stock ROM. That matters: `diag.c` cannot touch the SRAM once the Denso MCU is running, so it asks the Denso *software* to read/write for it, and only the DIAG16 mod implements that protocol (an extended serial diagnostics block at `0x8000`; the SAMC21 enters a phase with `0xDA` read, `0xDD` write-16 or `0xDC` write-8 and the ECU drives the rest — see `diag_protocol.md`). Against a stock ROM `diag.c` has nothing to talk to. So the image's low half is no longer `0xFF` padding but 264 bytes of diagnostic code at `0x8000`–`0x8107` plus `0x5F` fill; the engine ROM still occupies `0xC000`–`0xFFFF` and differs from the stock build in 57 bytes across five small regions — `C604`, `C67B`–`C67C` (the `jsr serial_diag_init` operand, which moves whenever the diag block changes size), `E204`, `FA72` and `FA8D`–`FAC0` — plus the recomputed checksum word at `FFDA`. Its self test sums the whole `8000..FFFF`, so the diagnostic block is checksum-protected too — that needed a one-line source change (`ld x, #unk_C000` → `ld x, #rom_start`, a new label at `.org 08000h`, mirroring how `D151804-0461_DIAG16_32K_JS` had always done it); the loop ends on X wrapping to `0000` rather than on a count, so the lower start costs only 64 outer passes instead of 32. (`image.c` used to carry a second `production_test.bin` image under `#if 0`; that is gone, regenerable from `hw/toyotune_lv_2p1/test code/production_test.bin` with `build_image.py ... --no-checksum`.)

      **Debug output and every `Panic` are disabled.** The whole API in `debug.h` sits inside an `#if 0`, whose `#else` branch defines `Debug()`, `Debug_Info()`, `Panic()`, `PanicFalse()` and `PanicNull()` to nothing. So none of the `Debug()` calls scattered through `main.c`/`diag.c` produce output (independently of `Debug_Init(3)` also being commented out in `main.c`), and all five `Panic` call sites — `main.c`'s CPLD version check, `sdl.c`'s buffer/channel assertions and its `Panic()` default, `os.c`'s ready-list assertion — are silently inert. To get any diagnostics, flip that `#if 0` and uncomment `Debug_Init(3)`; expect the re-enabled assertions to start firing on things that have been passing quietly.

      **`tools/build_image.py` — how `image.c` is produced.** `image.c` is a generated file; do not hand-edit it. The script assembles a ROM source from `roms/`, pads it to 32K, applies the OMODE patch and the `0xAA55` checksum, and emits the `DMCU_Image[]` array. `--verify` re-derives the image and compares it against the committed `image.c`, exiting 1 on drift; CMake exposes both as the `rom-image` and `verify-rom-image` targets, with the source selected from `TOYOTUNE_ECU`/`TOYOTUNE_CPU` (override with `-DTOYOTUNE_ROM_SOURCE=`). Confirmed to reproduce the committed image byte-for-byte from `roms/3S-GTE/D151803-9651/D151803-9651.ASM`. Two things about it are worth knowing before touching either it or the ROM build:

      - **It does not call `checksum.exe`/`scramble.exe`.** Both are MSVC builds that fail with `STATUS_DLL_NOT_FOUND` on machines lacking the redistributable (the DLL-load error noted elsewhere in this file), so both steps — a few lines of arithmetic each — are ported into the script. The assembler is *not* reimplemented; `roms/d8x_assembler/asm_d8x.py` is invoked with `-p 5F`.
      - **The checksummed range is read out of the image, not assumed — the ROMs in this repo disagree about it.** The self test is `ld x, #<start>` / `clr a` / `clr b` / `ld y, #0100h` / `add d, x + 00h` / `inc x` / `inc x` / `dec y` / `bne` … `cmp d, #0AA55h`; the script finds that byte sequence (`8E ?? ?? 52 53 8F 01 00 A7 00 1C 1C 1F 46 F9`) in the finished image and reads the `ld x` operand. All the 16K ROMs (`D151803-9651`, `-9661`, `-0461`, `-0471`, `-0481`, 3VZ `0680`) sum from `C000` because that is where they start; the 32K DIAG16 images (`D151803-9651_DIAG16_32K`, `D151804-0461_DIAG16_32K_JS`, `-0471`'s, and both `Jon_ST205_ECU` sources) sum from **`8000`** so their added diagnostic block is covered too. The 3S-GE `D151804-0401_DIAG16_32K` is the odd one out, still summing only `C000..FFFF` and leaving its own diagnostic code unchecked — it does not assemble, so it has not been brought into line. In these sources the loop reads `ld x, #rom_start`, `rom_start` being a label under `.org 08000h` — so grepping for `#unk_C000` alone will miss them. So no hardcoded value is right, and `checksum.exe`'s rule of inferring the start from the input file's *length* coincides with the truth only when a ROM's own start happens to equal it. Forcing `C000` on `D151804-0461_DIAG16_32K_JS` yields adjustment `6FC6` and an actual sum of `8F45` over `8000..FFFF` — a failed ROM self test. Full write-up in `INSTALL.md` §6.

      **`config.h` — which Denso CPU *and which car* this binary is for.** Two independent axes, each of which must be defined exactly once: `TOYOTUNE_CPU1`/`TOYOTUNE_CPU2` (which Denso CPU of the ECU this board is attached to) and `TOYOTUNE_ECU_MR2`/`TOYOTUNE_ECU_ST205` (which car). CMake passes both as compile definitions from `TOYOTUNE_CPU`/`TOYOTUNE_ECU`, so one source tree produces every combination without editing the header; the Studio project passes neither and falls through to the defaults. Everything that differs between the two boards is derived from these and nothing else: the DMA block sizes `TOYOTUNE_DMA_CPU1_TO_CPU2_SIZE` (38) and `TOYOTUNE_DMA_CPU2_TO_CPU1_SIZE` (34) — named by direction of travel, because a block is the same block whichever board is looking at it — the CAN identifier block (see below), and the ROM image in `image.c`. Both `TOYOTUNE_CPU2` and `TOYOTUNE_ECU_ST205` are deliberately an `#error`: each needs its own ROM image generated into `image.c` first, and failing the build beats silently flashing MR2 code into an ST205 ECU, or a CPU2 binary that parses CPU1's frame layout.

      **`sdl.c` — passive sniffer of the CPU1↔CPU2 link.** The ECU's two Denso CPUs talk to each other over a bidirectional 1 MHz USART, DMAing a block between them every 4 ms. `sdl.c` ("serial data logger") taps that link and extracts the data in realtime **without taking part in it**, and it is the source of the live values `main.c` forwards onto CAN. This is the same inter-CPU traffic the `roms/` notes describe via the shared DMA buffer (CPU1 address = CPU2 address + `0xDA`), so what it captures is exactly the `dmatx_*`/`dmarx_*` variables named in the two disassemblies.

      The passivity is in the configuration, not just the intent: `SDL_Init` sets `CTRLB = RXEN` with no `TXEN` and enables only the XCK and RX pads, never TX. Like `diag.c` it runs `CMODE` synchronous with `MODE(0)` external clock and a baud register of 0, so it slaves off the inter-CPU link's own 1 MHz clock instead of generating one; frames are 9-bit (`CHSIZE(1)`).

      Blocks are framed by **idle detection rather than by parsing**, which is the neat part. A DMAC channel receives into one of two 64-byte buffers, and every received beat emits a DMAC event that retriggers a one-shot 8-bit timer (TC0 for DMA channel 0, TC1 for channel 1) counting down from 100 on a 1 MHz clock. The timer can therefore only underflow once the line has been quiet for **100 µs** — on a link that bursts every 4 ms, that cleanly marks the end of a block. `SDL_DmaIdle` then derives the captured size from the DMA writeback descriptor, flips to the other buffer, restarts the transfer and invokes the callback.

      `main.c` registers `ECU_DmaData1` on SERCOM2 / DMA channel 1, and its first act is `if (RxSize == 38)`. That test is not a filter but an **integrity check that SDL captured the whole frame**: the idle timer will happily hand over a short block if the sniffer came up mid-burst or a burst was clipped, and parsing a partial block as `ECU_DmaData1_t` would silently misalign every field downstream of the truncation — producing plausible-looking but wrong telemetry rather than an obvious failure. Anything that is not exactly one full frame is dropped. The 64-byte DMA buffers leave headroom over the 38-byte frame so a complete capture is never truncated by the buffer itself.

      The two part numbers in `main.c`'s comments are **`D151804-0461` = CPU1 and `D151804-0471` = CPU2** — the same `+10` CPU1→CPU2 pattern as `D151803-9651`→`9661`, and `roms/3S-GTE/roms.txt` lists both as "JDM ST205". So the struct comment on line 26 and the `SDL_Init` comment on line 219 name *different CPUs of the same ECU*, not the same thing twice. The intent is for one firmware binary to serve both, with a **configuration bit identifying which CPU this board is attached to** (see the two-board topology note below) — that identity is what will select the right DMA frame layout, since the two CPUs send different payloads over the link.

      Note also that this callback runs in `TC1_Handler` interrupt context. That used to make `CAN_Tx()`'s unbounded busy-wait a hazard rather than a nuisance; the wait is bounded now (see the CAN notes below), but the constraint still stands — **anything called from here must be safe in interrupt context and must not block**.

      **`diag.c` — realtime read/write of the running Denso MCU.** This is the mode-2 path described above: with the SAMC21 off the bus, it asks the Denso software to read and write memory on its behalf *while the engine code is executing*, over a **1 MHz synchronous serial link on SERCOM0**. The SAMC21 is the clock **slave**: `Diag_Task` configures the USART with `CMODE` (synchronous), `CHSIZE(1)` (9-bit frames), `DORD`, `CPOL`, and a **baud register of 0** — the 1 MHz bit clock is generated by the Denso MCU and arrives on XCK, so the SAMC21 has no say in the rate. Pins are SERCOM0's `PA04` (PAD0, TX), `PA05` (PAD1, XCK) and `PA06` (PAD2, RX).

      The Denso MCU is the master and the SAMC21 answers it. The whole protocol runs out of `SERCOM0_Handler`, and **exactly one byte travels in each direction per 4 ms poll** — that is the central constraint, because the D8X receive buffer holds one byte and the NE crank interrupt preempts this ISR for ~350 µs at 7000 rpm. An earlier version sent two bytes per exchange and lost ~10% of reads to `SSD.6` overrun.

      `Diag_RxHandler` is now a single handler, not a chain: it classifies each frame by the 9th bit (mark `0xD0`–`0xDF` = the ECU announcing its state, mark `0x00`–`0x1F` = ADC traffic, space = payload), tracks `Diag_Mode` and `Diag_PayloadLeft`, and calls `Diag_GroupComplete` once an announcement and its payload have both arrived. That decides the single byte to send back. The task body is only woken afterwards, by `DIAG_SIGNAL_READ`/`DIAG_SIGNAL_WRITE`, to move bytes in and out of buffers. Because announcements and ADC traffic do not overlap, the SAMC21 keeps no state of its own beyond the last announcement — which is what makes the link self-resynchronising, with no timeout on either side.

      The SAMC21 enters a phase with `0xDA` (read), `0xDD` (write-16) or `0xDC` (write-8); the ECU drives every step after that. Writes are acknowledged by the ECU reading the location back and sending it, which `Diag_GroupComplete` compares against what was sent. **Every memory access is a single D8X instruction** — `ld d,[y]`, `st d,[y]`, `st a,[y]`, `ld a,[y]` — so nothing the protocol does can be seen half-finished by engine code. A 16-bit write holds the MSB in `serial_diag_wdata` (`0x0249`, carved out of the bottom of the stack) until the LSB arrives so the commit is one `st d,[y]`. Note a byte write is **not** a read-modify-write and needs no such trick; it exists as its own phase precisely so a single byte can be written without disturbing its neighbour.

      Reads are scheduled, not one-shot: `Diag_ReadEntry_t` items (address, size, period) live on a time-ordered linked list, and each completed read is re-inserted with its time advanced by `Period`, giving periodic sampling of ECU variables.

      A separate branch of `Diag_RxHandler` can snoop the ECU's **ADC** traffic, though it is currently compiled out (`DIAG_ADC_SNOOP` is `0`) and should be re-tested before being turned back on: a non-command frame other than `0x102` is taken as an ADC channel request, the channel is decoded as `(RxData >> 1) & 0x1F`, the USART's RX pad is retargeted from PAD2 to PAD0 (`SERCOM_UsartSetRxPad`) to capture the converter's two reply frames into `Diag->AdcData[channel]`, then switched back.

      **Current state — read before extending it.** The read and write paths are working and soaked at 7000 rpm (see `diag_protocol.md` for the numbers), but note: reads are **not** provably lossless — a 163k-read soak against a constant ROM location saw 6 wrong values, about 1 in 27,000, and nothing in the protocol detects a bad read, since only writes are verified by read-back. `Diag_Init()` no longer registers any reads (they are requested over CAN — see `diag_can.c`); the message API that would let other tasks add/remove reads (`Diag_HandleAddRequest` and friends) is still `#if 0`'d out and still does not compile (`Entry.Period` should be `Entry->Period`); and `Diag_ReadEntry_t.Repeat`/`ReadRepeat` are declared but unimplemented. Watch the counters `Diag_ProtocolResyncs`, `Diag_ReadStrays` and `Diag_TxDrainTimeouts` when something looks wrong — `Diag_ReadStrays` in particular is normally non-zero and large, because the ECU's block-read mode keeps streaming until a stop command lands and that command is often missed.

      `main.c` also declares the ECU DMA packet layouts for **D151804-0461** (`ECU_DmaData1_t` etc.) with field names that mirror the `dmatx_*`/`dmarx_*` variables in the `roms/` disassembly — when a DMA field's meaning is unclear on one side, cross-check the other.
      **`can.c`/`can.h` + `can_telemetry.c`/`.h` — the CAN driver and what it sends.** CAN0 is on `PA24`/`PA25` at 500 kbit/s (GCLK0 is 48 MHz, 16 tq per bit). `can.c` is the controller; `can_telemetry.c` is the **table-driven** layer above it, and is where telemetry content is changed — not `main.c`. A `CanTelemetry_Frames[]` table gives each frame an identifier, a period and a length, and a `CanTelemetry_Signal_t[]` table copies fields out of the DMA blocks by `offsetof()` into `ecu.h`'s structs, 2-byte signals big-endian. **Adding a signal means adding a table row, and adding an ECU family means adding a branch in `ecu.h`** — neither should need new code. Five frames go out on a tiered cadence off a single task tick: `FAST` every 20 ms (engine-event signals), `MEDIUM1`/`MEDIUM2` every 100 ms (thermal, electrical, ignition trim), `SLOW` every 500 ms (learned trims, flags, fault state), and `RAW` every 50 ms, which walks one 7-byte slice of the whole 72-byte DMA capture at a time with the slice index in byte 0, so the complete inter-CPU state is reconstructable off the bus. `toyotune.dbc` describes all of this for CAN tooling and is what `sw/python/can_monitor` decodes with — **keep the DBC in step with the tables**, since nothing enforces it.

      The **receive half — the part realtime tuning depends on — is not yet wired up**, which is not obvious from reading `CAN_Init()` alone: `CAN0->IE`/`ILE` enable the interrupt inside the peripheral, but nothing ever calls `NVIC_EnableIRQ(CAN0_IRQn)` and `CAN0_Handler` is still the weak `Dummy_Handler` alias from `Device_Startup/startup_samc21.c`, so nothing drains Rx FIFO 0. `CAN_FILTER_ID` (`0x45a`) is defined but unused and no filter element is installed (`can_rx_standard_filter` is commented out), so `GFC` currently shunts every message into FIFO 1 — and FIFO 1 is not a receive path at all, but overwrite-mode scratch that exists only to raise an interrupt per bus message for the errata 1.6.18 workaround. Note also that `0x45a` is written as an 11-bit standard ID while `CAN_Tx()` sets `CAN_TXBE_0_XTD` (29-bit extended); those need reconciling when the filter is added.

      Three more things to know before extending it. **CAN-FD is configured but off:** `DBTP` sets up a 3 Mbit/s data phase, yet the closing `CCCR = 0` leaves `FDOE`/`BRSE` clear, so the link is classic CAN at 500 kbit/s; the `TXESC.TBDS = DATA64` vs `RXESC` `DATA8` mismatch is a leftover of the same half-finished FD support. **There are two transmit entry points, and telemetry uses the standard one:** `CAN_TxStandard()` sends an 11-bit identifier (all telemetry), while `CAN_Tx()` sets `CAN_TXBE_0_XTD` for a 29-bit extended one — an identifier passed to the wrong one goes out silently mangled, since the extended path puts a standard ID in bits 28:18. Both pass `DataSize` straight into `CAN_TXBE_1_DLC()`, correct only for 0–8 bytes where DLC equals the byte count; if FD is ever enabled, lengths above 8 need the DLC *code*. **The transmit path is now bounded and self-healing** — this used to be a hazard note and is not any more: `CAN_TxWaitForSlot()` spins a bounded count rather than forever, returns failure and counts drops in `CAN_TxDropped`, and `CAN_Poll()` clears `CCCR.INIT` to recover from bus-off, counting recoveries in `CAN_BusOffRecoveries`, called each tick from `CanTelemetry_Task`. A deliberate spin count rather than a timeout, because the transmit path must stay callable from interrupt context where a SysTick-derived timeout could never expire. Note the drop counters are the diagnosis when telemetry goes quiet — read them before suspecting the bus. Bus-off recovery is written but **unexercised**: a merely silent bus cannot provoke bus-off (an error-passive transmitter seeing no ACK stalls at TEC = 128 by ISO 11898-1), so reaching it takes a real bit-error fault.

      **Intended topology: two ECU CPUs, two boards, one CAN bus.** The ECU contains two Denso CPUs (`D151803-9651` = CPU1 and `D151803-9661` = CPU2 in `roms/`), and the plan is for each to get its own Toyotune board — SAMC21 + shared SRAM + CPLD — with **both boards sitting on the same CAN bus**. Everything above describes one board against one Denso CPU; the second board is the same design against the other CPU.

      **Node identity is now solved, and the earlier warning here about both boards colliding on identical identifiers no longer applies.** A single firmware source serves both, with `TOYOTUNE_CPU`/`TOYOTUNE_ECU` selecting the ROM image served from `image.c`, the DMA block sizes, and a disjoint block of 11-bit standard identifiers from `TOYOTUNE_CAN_ID_TELEMETRY_BASE` — `0x400` for CPU1, `0x420` for CPU2, with `_FAST`/`_MEDIUM1`/`_MEDIUM2`/`_SLOW`/`_RAW` at `+0`…`+4`, kept well clear of `0x7DF`/`0x7E0`/`0x7E8` which OBD2 needs. It is a build-time define rather than the strapping pin once considered, **so the two boards run different binaries and flashing the wrong one is a real mistake to guard against**; a strap would still make one binary genuinely universal if that becomes worth having. What remains unfinished is the *receive* half, described above.

      The old worry recorded here — that `image.c` held a `D151803-9651` build while `main.c`'s DMA structs were labelled `D151804-0461`/`0471`, two different ECU families — is **resolved**. The layouts genuinely are common: both families use the same 38-byte and 34-byte blocks with the same field slots, differing only in base address (MR2 TX starts at `0x200`, ST205 at `0x1FA`), which is why one pair of structs in `ecu.h` serves both. The image and the parsing had simply come from different test sessions.

## Building a ROM

Each ECU directory's `Makefile` includes the shared `<family>/makefile.lib`, which defines the actual rules. From an ECU directory (e.g. `roms/3S-GTE/D151803-9651`):

```
make.exe rom            # assemble + checksum -> output/<name>.bin
make.exe rom_toyotune    # + pad to 32K for Toyotune flasher -> output/toyotune/<name>.bin
make.exe rom_techtom     # + scramble/XOR-encode for Techtom -> output/techtom/<name>.bin
make.exe clean           # remove output/
```

Use the `roms/bin/make.exe` on PATH (or invoke it explicitly), not a generic `make`, since these Makefiles use Windows-specific `mkdir`/`rmdir` logic (`win_path`, `make_dir`, `rm_dir` in `makefile.lib`).

From a family root (e.g. `roms/3S-GTE/Makefile`), the top-level `ROMS` list fans out the same targets across every ECU in that family: `make.exe rom`, `make.exe rom_toyotune`, `make.exe rom_techtom`, `make.exe clean`.

Build errors and assembler pass statistics land in `output/build.txt` (appended, not overwritten — check timestamps/tail when diagnosing a failed build). A `.lst` listing file is produced alongside the `.bin` showing address/opcode-byte/source correlation.

The assemble step (`ASM`/`ASMFLAGS` in `makefile.lib`) runs `roms/d8x_assembler/asm_d8x.py`, not `Tasm32.exe` — no `TASMTABS` needed for a build. `checksum.exe`/`scramble.exe` are unchanged and still do the checksum/pad/scramble steps.

## Working with the disassembly

- Symbol names are being progressively reverse-engineered from IDA's auto-generated defaults (`sub_C59B`, `unk_1C`, `loc_E16D`) into meaningful names (`iv6_ne_process`, `var_ign_advance_raw`, `CPR0`) as their purpose is understood. When editing `.ASM` files, match this convention: `sub_`/`loc_`/`unk_` prefixes mean "not yet understood," and renaming one should reflect a confirmed understanding of hardware behavior, not a guess.
- Cross-reference comments (`; DATA XREF: ...w`/`...r`) are IDA-exported and describe where a symbol is written/read from elsewhere in the same ROM — keep them accurate when moving/renaming code, since they're a primary navigation aid across a ~14k-line disassembly.
- The `roms/3S-GTE/gen3/*.md` files are the authoritative write-ups of subsystem behavior already reverse-engineered (and `roms/docs/toshiba-8x-*.md` for the MCU itself); consult them before re-deriving how ADC scanning, ignition scheduling, or knock retard already work, and extend them (rather than duplicating in comments) when new subsystems are understood.
- `D151803-9651` (3S-GTE, CPU1) is the most heavily annotated/documented ECU so far — treat it as the reference implementation when a similar routine appears in another engine family's disassembly.
- Before starting new reverse-engineering work on `D151803-9651`, read `roms/3S-GTE/gen3/session_journal.md` for current status (what's done, what's pending, established variable names) so renames stay consistent with prior sessions and don't duplicate completed work.
- **Encoding: these `.ASM`/`.asm` files are CP437 (the old IBM PC/DOS codepage IDA exported them in), not Latin-1/CP1252 as earlier notes here claimed.** Bytes ≥0x80 are CP437 box-drawing characters (decorative `SUBROUTINE`/section-divider banners); bytes 0x18/0x19 are CP437's control-range glyphs for `↑`/`↓` (IDA's xref-direction markers), appearing immediately before the trailing type letter in `; CODE XREF: ...+Nj/p/r/w/o` comments. **With exact-string edit tools this bites twice**: (1) a Read/Edit/Write round-trip that assumes UTF-8 will silently mangle every CP437 byte ≥0x80 into the Unicode replacement character `�` (U+FFFD) — this already happened, repeatedly and invisibly, to both `Claude/D151803-9651.asm` and `Claude/D151803-9661.asm` before it was caught and fixed (recovered from their still-CP437 buildable siblings; see session_journal.md) — so treat any `.ASM`/`.asm` file you're about to Edit as being at risk if it's been through prior tool round-trips and hasn't been explicitly converted; (2) even without that, an `old_string` reconstructed from what you *see* rendered may fail to match because 0x18/0x19 are invisible control bytes in normal rendering but present in the raw bytes. If an edit on a line ending in one of these xref comments doesn't match, either match only up to just before the final offset+letter, or target a line without a trailing xref comment instead. `Claude/D151803-9651.asm` and `Claude/D151803-9661.asm` have since been converted to proper UTF-8 (arrows as real `↑`/`↓` characters, banners restored) and no longer have this risk; every other `.ASM`/`.asm` file in the repo is still raw CP437 and still at risk from both issues.
- `D151803-9651` (CPU1) and `D151803-9661` (CPU2) each have a `Claude/` subfolder containing a working copy of the `.ASM` (`Claude/D151803-9651.asm`, `Claude/D151803-9661.asm`) that is *ahead* of the parent directory's `.ASM` (the one the Makefile actually builds) in renames/comments from ongoing reverse-engineering sessions. Edit the `Claude/` copy, not the parent one, when doing RE work — but be aware it can drift from the buildable source, so verify it still assembles to the same machine code (see below) rather than assuming comment/rename-only edits are always inert. The two ROMs communicate over a shared inter-MCU DMA buffer at a fixed address offset — when a variable's purpose is unclear on one side, check the other ROM's corresponding address for a computation that reveals it (see `roms/3S-GTE/gen3/fuel_calculation_system.md` for worked examples). **There are two different offsets, one per direction, and mixing them up silently lands you on an unrelated variable:**
  - **CPU2 → CPU1** (CPU2 `dmatx_*` = CPU1 `dmarx_*`): `CPU1_addr = CPU2_addr + 0xDA`. Confirmed via cross-named pairs, e.g. `dmarx_max_retard_23B_161` on CPU1 = `dmatx_max_retard_161` on CPU2.
  - **CPU1 → CPU2** (CPU1 `dmatx_*` = CPU2 `dmarx_*`): `CPU1_addr = CPU2_addr + 0x13B`. Confirmed via `dmatx_pim2`/`dmarx_pim2`, `dmatx_tps`/`dmarx_tps`, `dmatx_ect`/`dmarx_ect`, `dmatx_lambda_state`/`dmarx_lambda_state`, `dmatx_knock_retard_info`/`dmarx_knock_info`.

  Applying `0xDA` to a `dmatx` address lands inside CPU2's `var_serbus_rx` buffer rather than its DMA block — a real mistake made in a prior session, caught only because the result was obvious nonsense. If a cross-CPU lookup gives an implausible answer, check which offset you used before trusting it.
- **The `mov` instruction's operand order is `src, dest` — the opposite of `ld`/`st`, which are `dest, src`.** E.g. `mov x, d` means `D = X`, not `X = D`. This is confirmed by the technical reference's instruction table (`mov x, d` → "D ← X") and independently by the gold-standard `knock_mcu_update.ASM`'s annotation of `mov a, b` as "B = var_knock_info" where A held that value. It is very easy to misread and has caused real mistakes in this repo's comments, including in sessions after this note was needed. The shared math library's reversed comments in `Claude/D151803-9651.asm` **have now been swept**: ten `mov s, x` sites annotated "SP = X" were corrected to `X = SP` (the instruction immediately after each one uses `X` as a stack frame pointer — `div d, x + 00h`, `ld a, x + 01h` — which settles the direction independently), along with two explicit reversals. Comments there that merely describe what a register *holds* ("Y = result") were left as-is. The other `.ASM` files have **not** been swept. When a `mov`-involving computation matters, still re-derive the direction from the instruction table rather than trusting an existing comment — and note that getting it wrong is not academic: `sub_E865`'s middle blend hinges entirely on `mov x, d` meaning `D = X`, which changes its scale factor by 2x.
- **After editing an `.ASM`/`.asm` file, verify it still assembles to an identical binary** before considering the change safe, since renames/comments should never change actual bytes but a slipped instruction easily can. Assemble both the edited file and its buildable counterpart with `python roms\d8x_assembler\asm_d8x.py <input> <out.bin> <out.lst>` (prefer this over `roms\bin\Tasm32.exe` — see "Repository layout" above), then compare the two `.lst` listings with `python roms\verify_assembly_match.py <lst1> <lst2>` — **not** a raw `.out`/`.bin` byte diff or listing text diff. That script re-anchors the comparison on each `.lst`'s address column (confirmed to parse `asm_d8x.py`'s listing format correctly, not just tasm32's), because a single real edit (e.g. one extra/missing instruction byte) shifts every downstream absolute address reference by that same amount, and a naive diff reports hundreds of spurious "differences" that are really just correctly-recomputed jump/load targets following the one real change. Exit code 0 / "Total real edit regions: 0" means the binaries match. (`roms\bin\Tasm32.exe`/`roms\bin\checksum.exe`/`roms\bin\scramble.exe` may fail to run at all in some environments with an unrelated DLL-load error — that's not a sign anything is wrong with the ASM; this comparison doesn't need them.)
