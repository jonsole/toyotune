# Diagnostic Protocol v4 — 3S-GTE ECU CPU1 (D151803-9651 DIAG16)

The link that lets the Toyotune board read and write the ECU's memory **while the engine is running**. This is the protocol implemented by the `serial_diag_extended` block at `0x8000` in `D151803-9651_DIAG16_32K.ASM` and by `diag.c` on the SAMC21.

## Overview

The v2.1 board carries the SRAM the Denso MCU executes from, but only one of the two CPUs may drive that bus at a time. Once `DMCU_ResetDisable()` releases the Denso MCU, the SAMC21 has let go of the address and data lines and **cannot reach the SRAM at all**. To read or write ECU memory from that point on it must ask the Denso *software* to do it, over the 1 MHz synchronous serial link on SERCOM0.

That is why the ECU is the protocol master and the SAMC21 only ever answers. The ECU polls once per ADC scan slot — **every 4 ms** — and every exchange is anchored to one of those polls.

Two hardware facts shape everything else.

**The D8X receive buffer holds exactly one byte.** `serial_diag_extended` runs inside `int_vector_1_serial_rx`, which `int_vector_e_ne` (the NE crank interrupt, `IMASKL` bit 6) preempts for about 350 µs — one NE period at 7000 rpm with 24 teeth/rev. Protocol v1 answered each poll with two bytes 11 µs apart; when NE landed between them the second overran the first, `SSD.6` set, and the whole transaction was dropped. That was the ~10% read failure rate at 7000 rpm, confirmed by IMASK bisection and on the scope. **v4 takes exactly one inbound byte per poll**, so an overrun cannot happen.

**SIN0 is shared with the ADC converter.** Between polls the receive buffer fills with ADC traffic, so the protocol cannot be pipelined — a reply sent between polls would sit in the buffer for 4 ms and be overrun by the next ADC byte. The reply has to arrive *while the routine is looking*. Hence the flush at the top of every poll and the bounded wait at the bottom.

A fully-pipelined v2 was tried and failed for exactly this reason, with the ECU stuck announcing `DA`.

## Framing

11-bit frames at 1 MHz, LSB first, 9 data bits. The SAMC21 is a synchronous **slave**: `CMODE` synchronous, `CHSIZE(1)`, `DORD`, `CPOL`, and a **baud register of 0** — the bit clock is generated by the ECU and arrives on XCK, free-running. Pins are SERCOM0 `PA04` (PAD0, TX — shared with the ADC output, so TXEN is only asserted around a transmission), `PA05` (PAD1, XCK) and `PA06` (PAD2, RX).

The 9th bit is the parity/select bit and carries the frame's *kind*:

| Direction | 9th bit | Value | Meaning |
|---|---|---|---|
| ECU → SAMC21 | mark | `D0`–`DF` | diag state announcement |
| ECU → SAMC21 | mark | `00`–`1F` | ADC traffic — not ours |
| ECU → SAMC21 | space | any | diag payload byte |
| SAMC21 → ECU | mark (`SSD.0` set) | — | command |
| SAMC21 → ECU | space (`SSD.0` clear) | — | data byte |

Diag announcements (`D0`–`DF`) and ADC traffic (`00`–`1F`) do not overlap, so **the SAMC21 can classify every frame it receives with no state of its own**. That is what makes the link self-resynchronising: the SAMC21's only memory is the last announcement it heard, plus how many payload bytes that announcement owes.

On the ECU side the transmit parity is `SSD.1` — `setb bit1, SSD` for the mark announcement, `clrb bit1, SSD` before each space payload byte.

### `SSD` register (`$2B`)

| Bit | Meaning |
|---|---|
| 0 | received parity — command select |
| 1 | transmit parity — 0 = space (diag), 1 = mark (ADC) |
| 2 | output channel select |
| 4 | DOUT0 buffer empty |
| 6 | **receive overflow** |
| 7 | DIN0 buffer ready |

> Bit 6 is receive overflow. The ROM's own comment says so and is correct; `roms/docs/toshiba-8x-technical-reference.md` calls it "DIN0 bit 9 status" and is **wrong**. This was confirmed by measurement during the v1 failure investigation.

`SIDR_SODR` (`$06`) is the shared serial input/output data register.

## Structure of a poll

Every poll does the same four things:

```
.diag_flush         drain stale ADC bytes until SSD.7 clears
announce            send serial_diag_mode with mark parity
dispatch            jump through .diag_ann_vec — send a payload, or fall into the wait
.diag_wait          spin 10h iterations (~20 µs) for ONE byte, else ret
dispatch            jump through .diag_data_vec — one handler, one byte
```

The wait is sized from measurement: the SAMC21 answers about **9.4 µs** after the announcement ends (stable, measured on the scope), and a frame takes 11 µs to shift, so ~20 µs is needed. `10h` iterations is what v1 used for the same wait.

> **Do not raise the wait count.** It spins inside the serial ISR, and every extra iteration delays crank, ignition and injection.

---

## States

All twelve live states are `D0`–`DF`, so the low nibble is a dense 0–15 index into the dispatch tables.

| Mode | Meaning | Payload out |
|---|---|---|
| `DA` | idle / read: expect address MSB | — |
| `D0` | read: expect address LSB | — |
| `D8` | read result, address auto-increments | 2 (repeats) |
| `DD` | write16: expect address MSB | — |
| `D3` | write16: expect address LSB | — |
| `DE` | write16: expect data MSB (**held**) | — |
| `D4` | write16: expect data LSB (**commits**) | — |
| `DF` | write16 acknowledge, read-back | 2 (repeats) |
| `DC` | write8: expect address MSB | — |
| `D5` | write8: expect address LSB | — |
| `D6` | write8: expect data byte (**commits**) | — |
| `D7` | write8 acknowledge, read-back | 1 (repeats) |

`D1`, `D2`, `D9` and `DB` are unused and vector to resync.

**Commands accepted from the SAMC21: `DA`, `DD` and `DC` only** — the three phase entries. The internal sub-states are deliberately rejected, so a corrupt frame cannot drop the ECU into the middle of a phase.

---

## Read — 3 polls, ~12 ms

| Poll | ECU announces | SAMC21 sends | ECU does |
|---|---|---|---|
| 1 | `DA` | address MSB (space) | stash MSB → `D0` |
| 2 | `D0` | address LSB (space) | `D = A:B` is the address → `D8` |
| 3 | `D8` + **2 payload bytes** | command `DA` (mark) | `ld d,[y]`, Y += 2 → back to `DA` |

```
.diag_send_read:
                ld      y, serial_diag_address
                ld      d, [y]              ; read 2 bytes, Y += 2
                st      y, serial_diag_address
                clrb    bit1, SSD           ; parity space for payload
                st      a, SIDR_SODR
                div     d, #00h             ; inter-byte delay
                clrb    bit1, SSD
                st      b, SIDR_SODR
                jmp     .diag_wait
```

The read is `ld d, [y]` — **one instruction**, so it is an atomic 16-bit sample of the location. The two payload bytes go out with a `div d,#00h` between them for spacing, then the ECU re-enters `.diag_wait` *within the same poll* to catch the stop command.

---

## Write, 16-bit — ~7 polls, ~28 ms

| Poll | ECU announces | SAMC21 sends | ECU does |
|---|---|---|---|
| 1 | `DA` | command `DD` | → `DD` |
| 2 | `DD` | address MSB | stash → `D3` |
| 3 | `D3` | address LSB | `D = A:B` → `DE` |
| 4 | `DE` | *(nothing)* | address phase retired; SAMC21 task wakes to pack the word |
| 5 | `DE` | data MSB | **held** in `serial_diag_wdata` → `D4` |
| 6 | `D4` | data LSB | **`st d,[y]`**, Y += 2 → `DF` |
| 7 | `DF` + **2 payload bytes** | command `DA` | `ld d,[y]` read-back → `DE` |

Poll 4 sends nothing on purpose. Reaching `DE` is how the SAMC21 learns the ECU took both address bytes — that is the address phase acknowledged. It retires `WriteAddressReady` and signals the task to pack the first data chunk, answering on the *next* `DE` announcement. Without this handoff the write stalls with `WriteAddressReady` still set, which is why every write after the first once came back `BUSY`.

```
.diag_write_data:                           ; DEh - hold the MSB
                st      b, serial_diag_wdata
                ld      #0D4h, serial_diag_mode
                ret

.diag_write_data_lsb:                       ; D4h - commit both halves
                ld      a, serial_diag_wdata    ; D = A:B = the 16-bit value
                ld      y, serial_diag_address
                st      d, [y]                  ; ATOMIC 16-bit store; Y += 2
                st      y, serial_diag_address
                ld      #0DFh, serial_diag_mode
                ret
```

The MSB is **held, not stored**. Storing the halves in separate polls would leave 4 ms in which engine code could read a half-updated word. Holding it means the commit is a single `st d, [y]` — nothing can be scheduled between the halves. It also means an **abandoned write stores nothing at all** rather than half a word: if the SAMC21 goes quiet at `D4`, the ECU simply re-announces `D4` next poll and memory is untouched.

---

## Write, 8-bit — ~6 polls, ~24 ms

The same shape one exchange shorter, entered with `DC` instead of `DD`:

| Poll | ECU announces | SAMC21 sends | ECU does |
|---|---|---|---|
| 1 | `DA` | command `DC` | → `DC` |
| 2 | `DC` | address MSB | stash → `D5` |
| 3 | `D5` | address LSB | `D = A:B` → `D6` |
| 4 | `D6` | *(nothing)* | address phase retired |
| 5 | `D6` | data byte | **`st a,[y]`**, Y += 1 → `D7` |
| 6 | `D7` + **1 payload byte** | command `DA` | `ld a,[y]` read-back → `D6` |

There is no held half because there is nothing to hold: `st a, [y]` is a single-instruction byte store and is therefore already atomic.

**A byte write is not a read-modify-write.** It is offered as its own phase precisely because it is the operation to use when the neighbouring byte must not be disturbed — reaching a single byte through a *word* write would mean reading that neighbour and writing it back, and *that* read-modify-write is the thing that cannot be made atomic here.

---

## Block transfers

The payload states repeat rather than returning to idle:

- `D8` stays `D8` with the address already advanced, so if the SAMC21 stays quiet each further poll delivers the next word. A block read costs 2 address polls plus **1 poll per word**.
- `DF` drops back to `DE`, so a block write is one address phase then **3 polls per word**.
- `D7` drops back to `D6`, so a byte block write is one address phase then **2 polls per byte**.

A command ends any of these, and the SAMC21 sends one anyway to start its next request.

### The stray-word hazard

The ECU only listens for that stop command inside the ~20 µs window at the end of a poll, so **it is missed often** — measured at roughly one stray word per transaction at 7000 rpm (`Diag_ReadStrays` reached 1061 over a few hundred transactions).

Those stray words carry the contents of an address **two higher** than the one requested. Until 2026-09-04 `Diag_GroupComplete` accepted them as results, which re-completed an already-finished read entry: extra unsolicited `0x40B` CAN responses, and a stale value left to answer the *following* request. The SAMC21 now accepts a `D8` payload only while `ReadState == DIAG_READ_READY` and counts the rest in `Diag_ReadStrays`.

> **Bench scripts must match a `0x40B` reply on the opcode and the echoed address in bytes 2–3, never just take the first reply.** Taking the first one produced a completely false picture during development — apparently random values for constant ROM addresses, and an apparently churning stack — and cost a long detour before the raw frames were dumped.

## Atomicity

Every memory access the protocol makes is a **single D8X instruction**, so no interrupt can land inside one:

| Operation | Instruction | Width |
|---|---|---|
| read | `ld d, [y]` (`0x1B`) | 16-bit |
| write16 commit | `st d, [y]` (`0x8A`) | 16-bit |
| write16 read-back | `ld d, [y]` | 16-bit |
| write8 commit | `st a, [y]` (`0x82`) | 8-bit |
| write8 read-back | `ld a, [y]` (`0x1A`) | 8-bit |

Engine code can never observe a torn value, and the SAMC21 never verifies against one — the read-back is a coherent sample of the location, not bytes read a poll apart.

---

## RAM

State lives in three bytes of the direct page plus one byte of scratch:

| Address | Symbol | Purpose |
|---|---|---|
| `$7D`–`$7E` | `serial_diag_address` | current address, auto-incremented |
| `$7F` | `serial_diag_mode` | the state |
| `0x0249` | `serial_diag_wdata` | pending write MSB, held between polls |

`$77`–`$7C` belong to engine code and `$80` starts `var_diag_errors_1`, so the scratch byte could not go in the direct page. It sits at the **bottom of the stack**, which grows down from `stack_top` at `0x02FF` and so reaches `0x0249` last of all. The declaration splits the original block without moving anything:

```asm
unk_248:                .block 1        ; MUST stay at 0248h - copy_dma_rx compares X
                                        ; against #unk_248 as its loop sentinel
serial_diag_wdata:      .block 1        ; 0249h
                        .block 0B5h     ; rest of the stack (1 + 1 + B5h = B7h)
```

Two other locations were tried and rejected by measurement:

- **`0x00E0`** — live. Values marched `0xdb01, 0xdd00, 0xde01, 0xe001…`; it is reached by indexed addressing that a static xref search does not see.
- **`0x0307`–`0x03FE`** (the `.block 0F8h` after `table_knock_info`) — **not implemented RAM**. Reads back `0x0000` and ignores writes; `0x5AA5` did not stick at `0x0310`, `0x0320`, `0x0380` or `0x03F0`.

## Dispatch

Both dispatches are 16-entry `.dw` address tables indexed by `mode & 0Fh`:

```asm
                and     a, #0Fh              ; D0h..DFh -> 0..15
                shl     a                    ; ...times two, for a word table
                ld      y, #.diag_ann_vec
                add     y, a
                ld      y, y + 00h           ; Y = what this announcement owes
                jmp     y + 00h
```

- **`.diag_ann_vec`** — what the announced state owes right now: a payload, or just the wait.
- **`.diag_data_vec`** — where a data byte goes in this state. The states that *owe* a payload rather than expect one resync here, since a data byte arriving in them is a protocol error.

This is the ECU's own idiom, not a new one. The ADC scan in `int_vector_1_serial_rx` dispatches its channel handlers through `table_adc_handler` with the same five instructions and the same encodings (`AF 80`, `23 80`) at `0xFAD2`, and `add y, a` appears throughout the engine code.

They replaced compare chains of up to nine `cmp`/`beq` pairs. Beyond being constant-time, the table form has two properties worth keeping:

- **All sixteen slots are filled**, so a mode that somehow went bad lands on a real handler rather than falling off the end of a chain.
- It is an **address** table, not a table of branches, so it cannot be broken by a handler drifting out of an 8-bit branch reach. That is a live hazard in this block — branch range broke the build three separate times while the 8-bit write phase was being added.

`.diag_command` is deliberately still a compare chain: that byte comes straight off the wire and can be any value at all, so indexing on its low nibble would need a range check first — more code than the three compares it would save.

## Error handling

| Condition | Result |
|---|---|
| `SSD.6` set (receive overrun) | drain `SIDR_SODR`, mode → `DA` |
| data byte in a state expecting none | mode → `DA` |
| command other than `DA`/`DD`/`DC` | mode → `DA` |
| SAMC21 silent | `.diag_wait` times out, `ret`; same state re-announced next poll |
| acknowledge read-back mismatch | `WriteDataReady` stays set, the value is resent |

Resync is always "mode → `DA`". Because the SAMC21 keeps no state beyond the last announcement, it simply picks up from the next one — **neither side needs a timeout**.

SAMC21-side counters, useful when something looks wrong:

| Counter | Meaning |
|---|---|
| `Diag_ProtocolResyncs` | announcements that could not be accounted for |
| `Diag_ReadStrays` | streamed words discarded with no read pending |
| `Diag_TxDrainTimeouts` | frames that never got clocked out |

---

## SAMC21 side

The whole protocol runs out of `SERCOM0_Handler`. `Diag_RxHandler` classifies each frame, tracks `Diag_Mode` and `Diag_PayloadLeft`, and calls `Diag_GroupComplete` once an announcement and its payload have both arrived; that decides the single byte to send back. The task body is only woken afterwards, by `DIAG_SIGNAL_READ` / `DIAG_SIGNAL_WRITE`, to move bytes in and out of buffers.

`Diag_TxFrame` asserts `TXEN` only around the transmission, because TX shares PAD0 with the ADC output, and drains on **TXC** rather than DRE — on a synchronous slave link a frame leaves only when the ECU clocks it, so clearing `TXEN` on DRE alone can discard a byte that never went out. The drain is bounded so a stalled link cannot wedge the ISR.

Reads are scheduled: `Diag_ReadEntry_t` items (address, size, period) live on a time-ordered linked list and each completed read is re-inserted with its time advanced by `Period`. `Diag_TimerTick` raises `DIAG_SIGNAL_READ` while `ReadState == DIAG_READ_AVAILABLE` — without that the task could sleep with a completed read still pending and nothing left to wake it.

Write width is `Diag_t.WriteWidth`, fixed for the whole request because it selects which address-phase command is sent and therefore cannot change mid-transfer.

## CAN interface

Requests on **`0x40A`** (`TOYOTUNE_CAN_ID_DIAG_CMD`, = telemetry base + 10), responses on **`0x40B`** (+ 11). Base is `0x400` for CPU1 and `0x420` for CPU2.

**Request** (min 3 bytes):

| Byte | Field |
|---|---|
| 0 | opcode |
| 1–2 | address, big-endian |
| 3–4 | value, big-endian |
| 5–6 | period, ms |
| 7 | size — 1 or 2, default 2 |

**Response** (8 bytes): opcode, status, address (2), value (2), 0, 0.

| Opcode | Operation |
|---|---|
| `0x01` | read (one-shot) |
| `0x02` | write — `size` picks the width |
| `0x03` | add periodic read |
| `0x04` | cancel periodic read |
| `0x05` | cancel all |

| Status | Meaning |
|---|---|
| `0x00` | OK |
| `0x01` | bad opcode |
| `0x02` | no space |
| `0x03` | not found |
| `0x04` | bad size |
| `0x05` | busy |

For a write of `size` 1 the byte is the **low half** of the value field, so `0x00AB` writes `0xAB`. A write response is not sent until the ECU has acknowledged the data, so an `OK` means the write actually landed.

## Measured performance

At 7000 rpm on the bench, engine simulator running:

| | |
|---|---|
| Read | 12.0 ms median |
| Write, 8-bit | 23.5 ms median |
| Write, 16-bit | 27.6 ms median |
| Write+verify cycles | 420 with 0 mismatches, 0 bad status |
| Byte write neighbour disturbance | none, across `0x1234`/`0xFFFF`/`0x0000`/`0x5A5A` seeds |

### Residual read error rate

A continuous soak reading a **constant ROM location** (`0xC000`, always `0x5F5F`, so
any deviation is a protocol error and not memory changing under us) gave, over
163,766 consecutive reads at 7000 rpm:

| Outcome | Count | Rate |
|---|---|---|
| correct | 163,756 | |
| wrong value | 6 | ~1 in 27,000 |
| no response | 4 | ~1 in 41,000 |
| bad status | 0 | |
| stray reply | 0 | |

So reads are **not** provably lossless — the residual is about 0.006%, roughly one
bad read every 45 minutes at 34 reads/s. Short runs (the 6000-read checks used
during development) show zero and are not long enough to see it.

Nothing in the protocol currently detects a wrong value on a read: the payload is
unchecked, and only writes are verified, by read-back. **A caller that must not act
on a bad value should read twice and compare.** The cause has not been chased down;
candidates are a stray word landing exactly when a read is outstanding (which the
`ReadState` guard would not catch), or a frame corrupted on the wire.

Latency is dominated by the 4 ms poll interval — 3 polls for a read, 6–7 for a write — so dispatch cycles do not show up in it. The benefit of the table dispatch is ISR time and structure, not throughput.

### Throughput is not currently improvable by adding scan slots

Two attempts to add diag entries to `table_adc_channel` both failed: the first was a no-op, the second made reads *worse* (20.8 ms). The scan chain is driven by ADC replies and a diag slot hands it nothing to continue on, so the ~2 ms gap visible on the scope between diag and the following ADC read is the chain waiting for its next kick — probably `int_watchdog`'s `st b, SIDR_SODR` — rather than spare capacity.

Note also that `adc_debug_command` **double-increments** `var_adc_index` (`push a` / `jsr` / `pull a` / `inc a` on top of the `inc` in `adc_advance_index`), so the slot after a diag slot is unreachable. Slots 0 and 4 are dead and their `82h` entries are fillers — setting them to `80h` is a no-op, measured as 12.1 ms unchanged.

## History

| Version | Change |
|---|---|
| v1 | Two inbound bytes per exchange. ~10% of reads lost at 7000 rpm to `SSD.6` overrun when NE preempted between them. |
| v2 | Fully pipelined, no flush. Failed — ADC traffic fills the shared buffer between polls, so the ECU stuck at `DA`. |
| v3 | One inbound byte per exchange, flush retained. 0 failures. Writes still byte-at-a-time, so a 16-bit write was not atomic. |
| v4 | Data MSB held in `serial_diag_wdata` so a word write commits with one `st d,[y]`; separate 8-bit write phase; both dispatches converted to address tables. |
